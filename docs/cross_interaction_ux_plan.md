# План внедрения кросс-взаимодействий и контекстной навигации (UX/UI)

## 1. Контекст и мотивация
Текущий интерфейс DocuFlow состоит из изолированных функциональных модулей (Work Items, Task Board, Warehouse). Пользователям (особенно бригадирам и начальникам) приходится совершать много ручных действий для передачи информации между модулями. Цель данного плана — создать **бесшовную операционную среду**, где контекст сохраняется при переходах, а коммуникация между ролями происходит в один клик.

## 2. Анализ находок (UX симуляции)

### Находка 1: Потеря контекста при навигации
*   **Проблема:** Если бригадир фильтрует наряды по "Проекту А" в `WorkItemsView`, а затем переходит в `TaskBoard` для назначения задач, фильтр сбрасывается. Ему приходится заново искать нужные задачи.
*   **Решение (Global State):** Внедрение сессионного контекста. Выбранный проект или наряд должен сохраняться в `app.storage.user` и автоматически применяться как пред-фильтр на других экранах.

### Находка 2: Отсутствие "Сквозных ссылок" (Deep Linking)
*   **Проблема:** В аналитике или списке инцидентов фигурирует номер наряда/задачи, но кликнуть по нему нельзя. Нужно копировать ID, идти в другой раздел и вставлять в поиск.
*   **Решение (Routing Payload):** Модернизация функции `switch_view` для приема аргументов (например, `switch_view("work_items", {"highlight_id": 123})`).

### Находка 3: Разрыв коммуникации "Оператор ↔ Склад"
*   **Проблема:** Оператор видит, что для следующего батча нет металла. Он должен покинуть рабочее место или писать в сторонний мессенджер.
*   **Решение (Live Signaling):** Кнопка "Запросить материал" прямо в карточке батча (`BucketPanel`). На экране `WarehouseView` появляется пуш-уведомление и пополняется "Очередь подачи" в реальном времени.

### Находка 4: Ручное управление срочностью
*   **Проблема:** Для срочного "дореза" бракованной детали бригадиру нужно долго искать задачу в общем пуле `TaskBoard`.
*   **Решение (Flash-назначение):** Кнопка "Срочно на узел" прямо внутри карточки наряда (`WorkItemCard`). Она переводит задачу в статус `PLANNED` с высшим приоритетом и пушит ее в корзину оператора.

---

## 3. Архитектурные изменения

1.  **State Manager:** Создание класса `SessionContext` для обертки над `nicegui.app.storage.user`.
2.  **Умный Роутинг:** Изменение сигнатуры навигации в `MainLayout` и `main.py` для поддержки передачи параметров (dict).
3.  **Событийная модель UI:** Использование `ui.timer` на целевых экранах (например, Склад) для периодического (раз в 5-10 сек) опроса базы на предмет новых запросов снабжения, чтобы не перегружать P2P шину сложными UI-эвентами.

## 4. Пофазовый план реализации (TDD)

### Фаза 1: Фундамент роутинга и контекста
1.  **Настройка State:**
    *   Добавить сохранение `active_project_id` и `active_work_item_id` в хранилище NiceGUI.
2.  **Обновление MainLayout & main.py:**
    *   Изменить `switch_view(view_name: str, **kwargs)`.
    *   Адаптировать все вызовы меню для передачи параметров.

### Фаза 2: Контекстные переходы (Deep Links)
1.  **Связь WorkItems ↔ TaskBoard:**
    *   Добавить кнопку "К задачам" в `WorkItemCard`. Она вызывает `switch_view("task_board", {"filter_work_item": item.id})`.
    *   В `TaskBoardView._render_unassigned_panel` обрабатывать этот фильтр, подсвечивая или показывая только задачи выбранного наряда.
2.  **Связь Analytics/Incidents ↔ WorkItems:**
    *   Сделать ID нарядов в таблицах аналитики кликабельными.

### Фаза 3: Межролевые триггеры (Live Signaling)
1.  **Сигнал Снабжения (Оператор → Склад):**
    *   *UI:* Добавить кнопку 🚚 "Запросить металл" в `BatchCard` (только если есть `STOCK_ALERT` или вручную).
    *   *Backend:* Создать сущность `LogisticsRequest` (или использовать `Incident` с типом `MATERIAL_REQUEST`).
    *   *UI Склада:* Добавить в `WarehouseView` панель "Активные запросы снабжения" с `@ui.refreshable` и `ui.timer(10.0, refresh)`.
2.  **Flash-назначение (Бригадир → Оператор):**
    *   В `WorkItemCard` для каждой `TaskItem` добавить действие "Назначить срочно (Flash)".
    *   При клике открывается диалог выбора узла. Логика вызывает `TaskBoardSystem.lock_batch` напрямую из интерфейса нарядов.

### Фаза 4: Автоматизация обратной связи
1.  **Авто-инциденты:**
    *   При постановке задачи на паузу с чекбоксом "Проблема с материалом" (реализовано в предыдущем этапе) -> автоматически вызывать `IncidentSystem.report_incident()`.
2.  **Post-Completion Report:**
    *   При полном завершении наряда (`WorkItemStatus.DONE`) показывать бригадиру summary с отклонением по времени (Drift) и списком возникших инцидентов.

## 5. Ожидаемый результат
*   Снижение количества кликов для типовых операций (поиск задач наряда, запрос материала) на 50-70%.
*   Формирование единой информационной среды: кладовщик видит потребности оператора онлайн, бригадир мгновенно проваливается от макро-аналитики к конкретной проблеме.
