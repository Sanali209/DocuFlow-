# DocuFlow — Design Document

> **Версия:** 2.0 (на основе Master Plan v7)
> **Статус:** Living document — обновляется с каждой итерацией плана
> **Приоритет источников:** Текущий код > этот документ > Obsidian канвас

---

## 1. Назначение системы

DocuFlow — это распределённая производственная информационная система для цеха металлообработки. Она заменяет ручной бумажный учёт работ, устраняя проблемы:

| Проблема (сейчас) | Решение (DocuFlow) |
|---|---|
| Никто не знает, где лежат готовые детали | ProductionUnit + StorageLocation + поиск |
| GNC файлы изменились, оператор режет старую версию | NSMirrorService + хэш-мониторинг |
| Бригадир ведёт учёт на бумаге / голове | WorkItem + TaskItem + WorkerBucket |
| Нет синхронизации между лазерами | P2P FileBus + snapshot/sync |
| Расходники кончаются внезапно | Consumable + min_quantity алерт |
| Не фиксируются инциденты и простои | IncidentLog + WorkLog |
| Нет истории: кто, когда, что сделал | WorkLog (полный аудит) |
| Папка пришла, нестов нет — узнают позже | PENDING_CUTS статус + чат-алерт |
| Детали режутся повторно, хотя есть в запасе | STOCK_ALERT + автоблокировка TaskItem |

---

## 2. Контекст цеха

- **Производство:** Детали из листового металла для автобусов (Apollo и др.)
- **Оборудование:** Лазеры для резки металла. Каждый лазер = `Workplace` (узел системы)
- **Смены:** 2 смены
- **Роли:** Оператор (режет), Бригадир (планирует), Начальник (контролирует), Кладовщик (склад), Админ (IT)
- **Совмещение ролей:** Оператор + Бригадир может быть один человек
- **Среда:** Windows на всех машинах
- **Сеть:** Samba / CIFS сетевой диск (буква диска разная на каждом ПК)
- **Ограничение:** Нет прямого TCP между узлами — вся связь через файловую шину на сетевом диске

## 3. Источники данных

### 3.1 GNC файлы (основной источник)

Файлы программ резки для лазерного станка. Реальный формат:

```
(CK-AN Post V22.1 SP383  run on JUL 07 2025)    ← пост-процессор
(*MODEL HANS_G3015-REXROTH)                       ← модель МАШИНЫ, не проекта!
(1  PARTS)
(DATE JUL 07 2025)
(*SHEET 3250.0 1250.0 3.0 7 1 0.0 0.0)
  → sheet_x=3250, sheet_y=1250, thickness=3.0, sheet_qty=7
(Material:AA 5052-H32)
  → MaterialType.code = "AA 5052-H32"
(PART SIZE=3201.25  X 1136.361)
  → bbox ВСЕГО НЕСТA, НЕ отдельной детали!
(PART NAME:3433-11-004-G-1)
  → SKU = "3433-11-004-G" (version_letter="G", version_suffix="1")
(==== CONTOUR 1 ====)
N1005 G00X971Y485.361 ...
  → G-код контуров → bbox_x/y через SVGGenerator.calculate_bounds()
```

> **Критично:** `*MODEL` — это имя машины (`HANS_G3015-REXROTH`), **не** шаг проекта.
> Шаг (`SHLAV-2`) извлекается исключительно из **имени папки**.
> `PART SIZE` — bbox нестa целиком. Реальный bbox детали — только из парсинга G-кода контуров через SVGGenerator.

**SKU extraction:**
```
"3433-11-004-G-1" → sku="3433-11-004-G", version_letter="G", version_suffix="1"
Логика: последний БУКВЕННЫЙ сегмент = version_letter; цифры после = version_suffix (назначение TBD)
```

**Правило:** `_AUT.TXT` и `.Dsp` файлы игнорируются как ненадёжные.

### 3.2 Имена папок

```
SIDRA-353203-SHLAV-2-07.07.2025
  → sidra_number="353203", sidra_step="SHLAV-2", doc_date=2025-07-07
```

Если не парсится → fallback: `work_item_type=MIHTAV`, `project="Default"`.

### 3.3 Физические документы (бумажные наряды)

Регистрируются вручную бригадиром. Не сканируются, не парсятся. Только факт получения (`doc_received_at`).

## 4. Операционный цикл (8 этапов)

```
1. ПОЛУЧЕНИЕ РАБОТЫ
   Сканер → обнаруживает папку:
     С GNC:  WorkItem(NEW)          → чат-уведомление
     Без GNC: WorkItem(PENDING_CUTS) → алерт "нет нестов, сходить в раскрой"
              → сканер перепроверяет при каждом poll, авто-переход в NEW когда GNC появились
   Бригадир → регистрирует бумажный документ → WorkItem(REGISTERED)
   Инцидент "нет бумажных чертежей" → ChatMessage(type=INCIDENT) + фото

2. ПОДГОТОВКА К РАБОТЕ
   Бригадир → проверка материалов → Reservation (soft)
   Если нет → дозаказ → ChatMessage(type=ORDER)
   BatchEngine → автогруппировка TaskItem по MAT+THK+SIZE (DEFAULT_RULE)
   Бригадир → редактирует батчи → комментирует → приоритеты
   РУЧНАЯ БЛОКИРОВКА: TaskItem(BLOCKED) + lock_reason
   Проверка запаса → STOCK_ALERT → TaskItem(BLOCKED) если деталь уже есть
   УЧЁТ РАСХОДНИКОВ: ConsumableLog при завершении TaskItem; алерт при critical остатке

3. ПРИЁМ В РАБОТУ
   Оператор → видит батчи → резервирует → WorkerBucket
   FileBus REQ: lock_batch → Мастер подтверждает
   NSMirrorService → копирует GNC в локальную NS папку
   ВКЛИНИВАНИЕ: MIHTAV/REWORK перетаскивается в корзину → WorkLog(HANDOVER)
   ПРЕДУПРЕЖДЕНИЯ PartTemplate → видны оператору при открытии TaskItem

4. ВЫПОЛНЕНИЕ
   Оператор → меняет статус (planned → in_progress → on_hold → done)
   on_hold: обязательна причина + description
   ТРЕКИНГ ЛИСТОВ: sheets_done++ (прогресс-бар "5 из 8 листов")
   Оценка: estimated_minutes vs actual_minutes → drift%
   NS-зеркало: при изменении файла → диалог "Обновить NS / Оставить / Напомнить позже"
   Инциденты → IncidentLog + ChatMessage(type=INCIDENT) + attachments

5. ЗАВЕРШЕНИЕ
   TaskItem(DONE) → диалог "куда кладём?"
     Новая паллета: ProductionUnit(label_id="25-07-А-042")
     К существующей: live search по части label_id (≥2 символа)
   MaterialAudit(write_off) → факт списания листов
   Расходники: ConsumableLog(use, ref_task_item)

6. СКЛАДИРОВАНИЕ
   ProductionUnit → StorageLocation
   ПОИСК: по label_id / SKU / work_item / материалу / storage_location
   ОБРАТНЫЙ ПОИСК: деталь → паллета → стеллаж
   Split/merge паллет, частичный перевод в запас
   ДО-СИСТЕМНЫЕ ПАЛЛЕТЫ: is_pre_system=True, task_item_id=NULL
   "📂 Открыть папку" — subprocess → explorer.exe (с fallback текстовым путём)

7. РЕТРОСПЕКТИВНЫЙ ПОИСК
   PartLibrary: по SKU / bbox±допуск / кол-во отверстий / corner_count / текст
   ПРЯМОЙ: деталь X в наряде Y → TaskPart → TaskItem → WorkItem
   ОБРАТНЫЙ: деталь X везде → TaskPart[] → TaskItem[] → WorkItem[] → Project[]
   "В каких нарядах эта деталь?" "Где она сейчас?"

8. УПРАВЛЕНИЕ СКЛАДОМ
   MaterialStock: приход / списание / инвентаризация
   Consumable: сопла, линзы, лента + критический остаток
   MaterialAudit: полный аудит всех движений
   Передача смены: WorkerBucket handover + аннотации (handover_note, handover_from)
```

## 5. Матрица ролей

| Модуль | Оператор | Бригадир | Начальник | Кладовщик | Админ |
|---|---|---|---|---|---|
| Моя корзина (WorkerBucket) | FULL | READ | — | — | FULL |
| Доска задач (все узлы) | — | FULL | FULL | — | FULL |
| Чат + файлы | FULL | FULL | FULL | FULL | FULL |
| Наряды / WorkItem | READ | FULL | FULL | — | FULL |
| Батчинг | — | FULL | FULL | — | FULL |
| Склад материалов | — | READ | FULL | FULL | FULL |
| Расходники | — | READ | FULL | FULL | FULL |
| Склад деталей | Создать | READ | FULL | FULL | FULL |
| PartLibrary + Шаблоны | READ | FULL | FULL | READ | FULL |
| FolderScanner статус | — | READ | READ | — | FULL |
| Настройки | — | — | — | — | FULL |
| Отчёты | — | READ | FULL | — | FULL |
| Admin Panel | — | — | — | — | FULL |

> **Админ** = разработчик/поддержка, полный доступ для отладки.
> **Начальник** = все инструменты бригадира + аналитика + отчёты.
> **Оператор + Бригадир** — допустимое совмещение у одного пользователя.

## 6. Ключевые технические решения

| Вопрос | Решение | Обоснование |
|---|---|---|
| Кто сканирует | Только мастер-узел | Один источник правды |
| Триггер сканирования | Periodic polling (async) | Samba не поддерживает inotify надёжно |
| Хранение путей | Только относительные от scan_root | Буква диска разная на каждом ПК |
| Изменение файлов | MD5 hash + WorkLog + atomic_write | Детекция без перемещения, атомарность |
| Исходные файлы | Не трогаем | Сеть = read-only источник |
| Синхронизация узлов | FileBus + Snapshot | Нет TCP соединений |
| GNC → локальный диск | NSMirrorService (60s, timeout=30s) | Автоматика читает из локальной NS папки |
| ID паллеты | "25-07-А-042" (human-readable) | Нет QR-сканера, нужен ввод вручную |
| Конфигурация путей | LOCAL .env | Глобальная синхронизация недопустима |
| Bbox детали | SVGGenerator.generate_thumbnail() → (data_w, data_h) | PART SIZE = bbox неста, не детали |
| SKU в PartLibrary | "3433-11-004-G" (base + version_letter) | version_suffix сохраняется в TaskPart, но не в PK |
| Идемпотентность сканера | upsert по file_path (relative) | Повторный poll не создаёт дублей |
| Конкурентное сканирование | filelock (.docuflow.lock в scan_root) | Защита от параллельного запуска |
| Поиск деталей | bbox±tolerance + hole_count + corner_count | Поиск по геометрии без точного SKU |

## 7. Открытые вопросы (не закрыты с v4)

> **Q1: version_suffix в SKU** (`"3433-11-004-G-1"` → суффикс `"1"`)
> Что означает цифра после буквы версии? Инкремент? Номер экземпляра?
> **Пока:** сохраняем в `TaskPart.version_suffix`, не используем для идентификации.

> **Q2: ChatMessage синхронизация**
> Чат синхронизируется через FileBus broadcast или хранится в БД для истории?
> **Рекомендация:** хранить в БД (для ретроспективы смены), broadcast только для real-time уведомлений.

> **Q3: WorkerBucket — один или много TaskItem одновременно?**
> Оператор берёт батч целиком (все TaskItem в батче) или по одному?
> **Текущее:** берёт батч → все его TaskItem попадают в корзину.

> **Q4: Attachments / manifest**
> Вложения (фото, PDF) хранятся в `attachments/<uuid>/` с `manifest.json`.
> Нужен единый механизм для IncidentLog, ChatMessage и WorkItem.

## 8. Границы системы (in/out of scope)

### В рамках системы
- Автоматическое обнаружение нарядов по сетевой папке (с идемпотентным upsert)
- Управление производственными задачами (batch/task/status/time tracking)
- Учёт материалов, расходников, готовой продукции (split/merge паллет)
- Оперативная коммуникация (чат с типами и вложениями)
- Ретроспективный поиск деталей по SKU, bbox, hole_count (прямой и обратный)
- Отчёты по шаблонам (Jinja2 HTML → PDF через weasyprint)
- NS-зеркало GNC файлов для операторов (с timeout защитой)
- Регистрация до-системных паллет (is_pre_system)
- ViewPreset (Notion-подобные пресеты вида — личные + глобальные)

### Вне рамок системы
- Интеграция с ERP завода (не планируется в v1)
- Автоматическое создание нарядов из внешних систем
- Управление станком (только мониторинг)
- Мобильное приложение (только Windows desktop NiceGUI)
- Резка труб и прутков (backlog, не MVP)
