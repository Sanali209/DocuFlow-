## Общая оценка

Архитектура проекта продуманная и последовательная. Вертикальные слайсы применяются единообразно, DI-скоупы в целом корректны, P2P-протокол на файловой шине спроектирован грамотно. Код самодокументирован, константы именованы, docstring-и присутствуют. Основные риски сосредоточены в жизненном цикле фоновых задач, утечке сессий при старте и одном захардкоженном секрете.

## Критические проблемы

### 1. `_handle_critical_failure` не останавливает приложение

**Файл:** `src/docuflow/application/bus/orchestrator.py`

```python
async def _handle_critical_failure(self, error: Exception) -> None:
    logger.critical(f"P2P CRITICAL FAILURE: {error}. Triggering emergency shutdown.")
    await self.on_shutdown()  # только отменяет CancelScope
```

`on_shutdown()` отменяет `CancelScope` — и всё. FastAPI/NiceGUI процесс продолжает работать без P2P, без синхронизации, без координации. Никакого сигнала наружу нет. Нода деградирует молча.

**Что сделать:** добавить флаг `self._failed = True`, который отображается в health-check / admin-view, либо пробрасывать исключение в TaskGroup чтобы процесс падал явно.

---

### 2. `asyncio.create_task` вместо структурированного параллелизма

**Файл:** `src/docuflow/application/bus/orchestrator.py`, метод `on_startup`

```python
self._orchestration_task = asyncio.create_task(self._run_orchestration_master())
```

В коде есть комментарий: *"This will be properly bound to the SDK's global TaskGroup in Task 3.1"* — этот TODO до сих пор открыт. `asyncio.create_task` обходит абстракцию AnyIO, задача fire-and-forget, исключения из неё глотаются если не делать явный `await`. `_cancel_scope` создаётся снаружи, но входится внутри задачи — работает только случайно.

**Что сделать:** передать `TaskGroup` из lifespan в оркестратор и использовать `tg.start_soon`.

---

### 3. Утечка сессии при старте SDK

**Файл:** `src/docuflow/sdk.py`, метод `on_startup`

```python
async with self.request_scope() as req:
    self._projects = await req.get(ProjectSystem)
    await self._projects.on_startup()
    # ... аналогично для parts, consumables, production, notifications
```

`ProjectSystem`, `NotificationService` и другие — `REQUEST`-скоупные системы. Их сессия живёт только внутри блока `async with`. После выхода из блока сессия закрыта, но `self._projects` и остальные ссылки остаются живыми. Если любая из этих систем обратится к `self.session` позже — получим ошибку закрытой сессии.

**Что сделать:** не хранить REQUEST-скоупные системы как долгоживущие атрибуты SDK. Для операций при старте (seed, bootstrap) — выполнять их внутри блока и не сохранять ссылку.

## Высокий приоритет

### 4. `P2POrchestrator.__init__` принимает `None` для всех зависимостей

```python
def __init__(
    self,
    config: Config,
    coordination: "CoordinationSystem" = None,  # type: ignore[assignment]
    bus: "FileBusSystem" = None,  # type: ignore[assignment]
    ...
```

`is_leader` упадёт с `AttributeError` если `_coordination is None`. `type: ignore` заглушает type checker на реальный runtime-риск. Паттерн явно введён для тестов.

**Что сделать:** использовать `Optional[CoordinationSystem]` с явной проверкой, или требовать все зависимости и использовать фабрику/фикстуру в тестах.

---

### 5. Ручное кэширование SDK в `AppProvider` — лишнее

**Файл:** `src/docuflow/infrastructure/di.py`

```python
@provide(scope=Scope.APP)
def get_sdk(self, container: AsyncContainer) -> SDK:
    if hasattr(self, "_sdk") and self._sdk is not None:
        return self._sdk
    self._sdk = SDK(container)
    ...
```

`Scope.APP` уже гарантирует singleton-семантику в Dishka. Ручной кэш на инстансе провайдера избыточен и может маскировать баги при пересоздании контейнера. SDK привязывается к lifetime провайдера, а не контейнера.

**Что сделать:** убрать ручной кэш, доверять скоупу.

---

### 6. SDK резолвится дважды из разных контейнеров в `lifespan`

**Файл:** `src/docuflow/main.py`

```python
# шаг 2 — из request-контейнера
async with _container() as request_container:
    sdk_instance = await request_container.get(SDK)
    fastapi_app.state.sdk = sdk_instance

# шаг 4 — из app-контейнера напрямую
sdk_instance = await _container.get(SDK)
await sdk_instance.on_startup()
```

Сейчас это работает только благодаря ручному кэшу из п.5. Если кэш убрать — два разных инстанса SDK, `on_startup` вызывается не на том, что лежит в `fastapi_app.state`.

**Что сделать:** убрать шаг 2, резолвить SDK только из `_container` напрямую.

### 7. Захардкоженный секрет в `main.py`

ui.run_with(app, title="DocuFlow Portal", storage_secret="docuflow_nicegui_shh")

## Средний приоритет

### 8. Port-killer в `main.py` — Windows-only, с кириллической кодировкой

```python
result = subprocess.run(
    ["netstat", "-ano", "-p", "TCP"], capture_output=True, text=True, encoding="cp866"
)
```

`cp866` — DOS-кодировка для русского языка. Упадёт на любой другой ОС или локали (ошибка глотается `except Exception`). Логика убийства порта не относится к entrypoint приложения.

**Что сделать:** перенести в `scripts/kill_port.py`, добавить guard `if sys.platform == "win32"`.

---

### 9. `switch_view` в `main.py` — растущий if/elif по именам вьюх

```python
if view_name in ["dashboard", "warehouse", "admin", "chat", "incidents"]:
    resolved_deps.append(layout)

if view_name == "work_items" and "filter_text" in kwargs:
    ...
elif view_name == "task_board":
    ...
```

Каждая новая вьюха с нестандартным поведением требует правки этой функции. Это ловушка для поддержки.

**Что сделать:** добавить флаги в `ViewInfo` (`needs_layout: bool`, `accepts_filter_kwargs: bool`) и сделать dispatch data-driven.

### 10. Избыточный DEBUG-лог в `_polling_worker`

```python
logger.debug(
    f"Orchestrator [{self.config.node_id}]: Polling bus (interval: {self.config.bus_poll_interval}s)"
)
```

При интервале 5 секунд — 12 строк в минуту на ноду, ~50 строк/мин на кластер из 4 нод. Чистый шум.

**Что сделать:** убрать или заменить на `logger.trace`.

### 11. `TaskBoardSystem` (REQUEST) держит ссылку на `NSMirrorService` (APP)

**Файл:** `src/docuflow/infrastructure/di.py`

```python
@provide(scope=Scope.REQUEST)
def get_task_board(
    self,
    ...
    ns_mirror: NSMirrorService,  # APP-скоуп
    ...
) -> TaskBoardSystem:
```

Dishka это разрешает, но если `NSMirrorService` имеет изменяемое состояние без защиты от конкурентного доступа — это потенциальный race condition при параллельных запросах.

**Что сделать:** убедиться что `NSMirrorService` thread/task-safe, или задокументировать это явно.

## Низкий приоритет / Стиль

### 12. `WorkItemStatus.FOLDER_NO_DOC` и `DOC_NO_FOLDER` не имеют переходов в `VALID_TRANSITIONS`

**Файл:** `src/docuflow/features/work_items/system.py`

Эти статусы есть в enum, сканер может их выставлять, но из них нет ни одного валидного перехода. WorkItem в таком статусе — застрявший навсегда.

**Что сделать:** добавить переходы (например в `REGISTERED` или `PENDING_CUTS`) или явно задокументировать что это терминальные диагностические статусы.

---

### 13. `...` и комментарий `# (other methods)` в теле `AppProvider`

```python
class AppProvider(Provider):
    """..."""
    ...
    # (other methods)
    @provide(scope=Scope.REQUEST)
    def get_search_system(...):
```

`...` в теле класса с методами — no-op, комментарий вводит в заблуждение. Артефакт рефакторинга.

**Что сделать:** удалить.

---

### 14. `BaseSystem` принимает `session` как опциональный

Системы, которым сессия нужна, могут быть сконструированы без неё и упадут только в runtime при обращении к `self.session`. Системы без сессии (например `FileBusSystem`) наследуют базу с подразумеваемым владением сессией.

**Что сделать:** рассмотреть разделение на `BaseSystem` (без сессии) и `BaseDBSystem(BaseSystem)` (с обязательной сессией).
