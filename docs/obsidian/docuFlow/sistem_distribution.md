Распределенная система на базе такой «файловой шины» будет работать как **сеть независимых агентов**, которые общаются асинхронными сообщениями. Главное отличие от классического веба — здесь нет «ожидания ответа» в рамках одного HTTP-соединения.

Логика переходит от линейной к **событийно-ориентированной (Event-Driven)**.

---

## 🏗️ Логическая схема взаимодействия

Система делится на три слоя: **Интерфейс**, **Локальное хранилище** и **Транспортный агент**.

### 1. Узел (Рабочее место лазера)

Узел не ждет Координатора, чтобы показать данные пользователю.

- **Чтение:** NiceGUI отображает данные из локальной SQLite.
    
- **Действие:** Когда рабочий нажимает «Взять наряд», Узел:
    
    1. Записывает изменение в локальную БД (статус `pending_confirmation`).
        
    2. Создает файл `REQ_LASER1_COORD_lock_123.json` в шине.
        
- **Синхронизация:** Фоновый процесс мониторит шину. Когда появляется `RES_COORD_LASER1_lock_123.json` с подтверждением, статус в локальной БД меняется на `active`.
    

### 2. Координатор (Центральный мозг)

Координатор работает как бесконечный цикл (через `watchdog` или `polling`):

1. **Слушает шину:** Видит новый `REQ`.
    
2. **Валидация:** Проверяет в Мастер-БД, не занят ли этот наряд другим лазером.
    
3. **Принятие решения:** * Если всё ок: Обновляет Мастер-БД и пишет `RES_..._OK`.
    
    - Если наряд уже занят: Пишет `RES_..._ERROR_ALREADY_TAKEN`.
        
4. **Синхронизация файлов:** Если наряд завершен, Координатор сам перемещает физические файлы чертежей в папку `/DONE/` на сетевом диске.
    

---

## 🔄 Основные сценарии (Flows)

|**Сценарий**|**Логика**|
|---|---|
|**Холодный запуск**|Узел ищет в `/SNAPSHOTS` самый свежий JSON-файл и подтягивает его в локальную SQLite. Затем шлет `REQ_..._sync_delta` для получения последних изменений.|
|**Бронирование (Lock)**|Самый критичный момент. Узел считает наряд своим только после получения `RES` от Координатора. До этого момента в GUI висит «Песочные часы».|
|**Складской учет**|Оператор вводит «Полка А1». Узел шлет `REQ_..._update_loc`. Координатор обновляет мастер-запись, чтобы Бригадир на своем узле мгновенно увидел местоположение.|
|**Сбой связи**|Если файл `REQ` лежит в шине 2 минуты и не исчезает — Узел подсвечивает интерфейс красным: «Связь с сервером потеряна, работа в офлайн-режиме».|

## 🛠️ Как это выглядит в коде (Псевдо-логика)

**На стороне Узла (NiceGUI + Background Task):**

Python

```
async def on_click_start_job(order_id):
    # 1. Сразу меняем UI, чтобы рабочий видел реакцию
    order.status = "waiting" 
    
    # 2. Кидаем запрос в шину
    req_id = bus.send_request("COORD", "START_ORDER", {"id": order_id})
    
    # 3. Ждем ответа в фоновом режиме
    while not bus.has_response(req_id):
        await asyncio.sleep(1)
    
    # 4. Получили ответ — обновляемся окончательно
    result = bus.get_response(req_id)
    if result["status"] == "OK":
        order.status = "in_progress"
    else:
        notify("Ошибка: Наряд уже взят другим!")
```

## ⚡️ Почему эта логика живучая

1. **Устойчивость к «миганию» сети:** Если Samba отвалилась в момент записи `REQ`, файл просто не появится. Узел это поймет и попробует снова.
    
2. **Очередь сообщений:** Если 10 лазеров одновременно нажмут «Старт», файлы лягут в папку. Координатор обработает их по очереди (по времени создания файла), обеспечив честную конкуренцию.
    
3. **Прозрачность для админа:** Чтобы понять, почему «завис» лазер, вам не нужны логи в базе. Вы просто открываете общую папку и видите: «Ага, файл ответа для Лазера-1 висит уже час, значит Лазер-1 его не прочитал».
