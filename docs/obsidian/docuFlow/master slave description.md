Это отличный вопрос, который подводит нас к концепции **Гибридного Узла**. В твоей системе каждый экземпляр SDK — это «Шрёдингеровский кот», который одновременно является и рабочим терминалом (**Slave/Client**), и потенциальным сервером (**Master/Coordinator**).

Чтобы это работало без конфликтов и «каши» в данных, нам нужно четко разделить потоки логики внутри одного процесса.

---

## 1. Когда и как Узел получает ID (Global Identity)

В распределенной системе **ID не может быть просто `autoincrement` из базы**, потому что у каждого узла своя база.

- **Node ID:** Берется из конфига (`.env`) или аппаратного адреса (MAC-адрес). Например: `LASER_01`, `BENDING_02`.

- **Transaction ID (REQ_ID):** Генерируется узлом в момент действия. Формат: `{NODE_ID}_{TIMESTAMP}_{COUNTER}`.

    - _Пример:_ `LASER1_20260401_001`. Это гарантирует уникальность файла в шине Samba.

- **Entity ID (Task/Order):** Создается **только Мастером**. Когда узел хочет создать новый наряд, он шлет `REQ_CREATE_TASK`. Мастер присваивает ему `UUID` и возвращает в `RES`.


---

## 2. Работа Гибридного Узла (Dual-Mode)

Твой SDK должен работать в двух параллельных потоках (Threads или Async Tasks).

### Поток А: Интерфейс и Клиент (Всегда активен)

Этот поток отвечает за NiceGUI и локальные действия.

1. Читает `local.db` для отображения списка.

2. При клике на кнопку — пишет файл `REQ_...` в шину.

3. Слушает шину на предмет `RES_...` для своего `Node_ID`.


### Поток Б: Диспетчер Мастера (Активен только у Лидера)

Этот поток просыпается только если узел захватил `.coordinator.lock`.

1. **Загрузка:** Скачивает последний `SNAP_{id}_{ts}.json` из Samba (если он содержит более свежие записи, чем локальный).
2. **Цикл:** Сканирует папку `/BUS/INBOX` на наличие любых `REQ_`.
3. **Логика:** Обрабатывает запросы, пишет в базу, выкладывает `RES_` в `/BUS/OUTBOX`.


---

## 3. Как это выглядит в коде (Аллокатор-Блокатор)

Твой Аллокатор при старте запускает фоновую задачу мониторинга роли.

Python

```
class FactorySDK:
    def __init__(self, session: Session, node_id: str):
        self.node_id = node_id
        self.session = session
        self.is_leader = False

    async def run_leader_election(self):
        """Фоновая задача: пытаемся стать мастером"""
        while True:
            if try_acquire_lock(self.node_id): # os.rename на Samba
                if not self.is_leader:
                    await self.promote_to_leader()
            else:
                if self.is_leader:
                    await self.demote_to_slave()
            await asyncio.sleep(15)

    async def promote_to_leader(self):
        self.is_leader = True
        # Подгружаем мастер-базу и запускаем обработчик шины
        self.bus_controller = BusCoordinatorSystem(self)
        print(f"Node {self.node_id} is now the MASTER")

    async def demote_to_slave(self):
        self.is_leader = False
        self.bus_controller = None
```

## 4. Конфликт "Сам себе Мастер"

Если узел стал Мастером, он всё равно остается терминалом для рабочего.

**Как он обрабатывает свои же запросы?**

- **Правило:** Даже если я Мастер, я всё равно пишу `REQ` файл в шину.

- **Почему:** Это упрощает код. Моему "Потоку Мастера" всё равно, чей это запрос — мой или соседа. Он просто видит файл, обрабатывает его и кладет ответ.

- **Профит:** Весь цикл обмена данными проходит через файловую систему. Это гарантирует, что база данных всегда будет в консистентном состоянии, независимо от того, кто нажал кнопку.


---

## 5. Жизненный цикл данных при смене ролей

|**Событие**|**Действие Узла**|
|---|---|
|**Старт**|Генерирует/берет свой `Node_ID`. Читает `local.db`.|
|**Выборы**|Успех! Становится Мастером. Загружает последний JSON-снапшот из Samba.|
|**Работа**|Принимает файлы от других, обновляет базу, делает JSON-снапшот в Samba раз в несколько минут.|
|**Крах**|Выключили питание. `.coordinator.lock` протухает через таймаут (по умолчанию 60 сек).|
|**Восстановление**|Другой узел (например, `LASER_02`) видит, что замок свободен, забирает его, объединяет данные из последнего снапшота и продолжает с того же места.|

**Что думаешь про идею "Запроса к самому себе через файл"?** Это кажется лишним кругом, но это делает логику "железобетонной", так как у тебя нет разницы в коде для Мастера и Слейва.

В контексте **FastAPI** реализация гибридного узла (Master/Slave) требует использования **Lifespan-событий** и фоновых задач (`Background Tasks` или `asyncio.create_task`).

Поскольку FastAPI — это асинхронный фреймворк, мы можем запустить «Двигатель Выборов» и «Двигатель Шины» параллельно с обработкой HTTP-запросов от NiceGUI.

---

## 1. Точка входа: Lifespan

В FastAPI `lifespan` — это идеальное место для инициализации Аллокатора и запуска фоновых процессов, которые живут всё время работы приложения.

Python

```
from contextlib import asynccontextmanager
from fastapi import FastAPI
import asyncio

@asynccontextmanager
async def lifespan(app: FastAPI):
    # 1. Инициализация SDK (Аллокатор)
    sdk = FactorySDK(node_id="LASER_01", smb_path="//SERVER/BUS")
    app.state.sdk = sdk

    # 2. Запуск фоновых "движков"
    election_task = asyncio.create_task(sdk.run_leader_election())
    bus_watcher_task = asyncio.create_task(sdk.run_bus_watcher())

    yield # Здесь приложение работает (FastAPI + NiceGUI)

    # 3. Грамотное завершение (Shutdown)
    election_task.cancel()
    bus_watcher_task.cancel()
    await sdk.cleanup()
```

## 2. Реализация Логики в SDK (Аллокатор)

Твой SDK должен управлять переключением состояний. Когда `election_task` понимает, что узел стал Лидером, он активирует логику Координатора.

### Механизм "Шины" через файлы

Используем библиотеку `watchfiles` или стандартный `asyncio` для опроса папки.

Python

```
class FactorySDK:
    def __init__(self, node_id, smb_path):
        self.node_id = node_id
        self.smb_path = smb_path
        self.is_leader = False
        self.session = None # Сессия SQLModel

    async def run_bus_watcher(self):
        """Фоновая задача, которая слушает файлы REQ"""
        while True:
            if self.is_leader:
                # ЛОГИКА МАСТЕРА:
                # 1. os.listdir(self.smb_path) -> ищем REQ_*.json
                # 2. Обрабатываем через SQLModel
                # 3. Пишем RES_*.json
                await self.process_incoming_requests()

            # ЛОГИКА СЛЕЙВА (Клиента):
            # 1. Ищем RES_ для нашего Node_ID
            # 2. Обновляем локальную БД
            await self.check_responses_for_me()

            await asyncio.sleep(1) # Частота опроса шины
```

## 3. Взаимодействие с NiceGUI (Frontend)

NiceGUI работает внутри того же процесса FastAPI. Когда рабочий нажимает кнопку, мы используем `app.state.sdk`, чтобы отправить запрос.

Python

```
# В коде NiceGUI (ui.py)
from fastapi import Request

async def start_job_ui(request: Request, order_id: str):
    sdk = request.app.state.sdk

    # 1. Создаем запрос (просто пишем файл на Samba)
    req_id = await sdk.send_request("START_ORDER", {"id": order_id})

    # 2. Ждем ответа (через локальную БД или событие)
    ui.notify("Запрос отправлен координатору...")

    # NiceGUI может подписаться на обновление локальной БД
    # Как только фоновый 'run_bus_watcher' запишет ответ в БД,
    # интерфейс обновится реактивно.
```

## 4. Схема "Запроса к самому себе"

Это самый важный момент для автономности. Даже если FastAPI-узел является Мастером, он проходит полный путь:

1. **NiceGUI (UI)** -> Вызывает метод `sdk.send_request()`.

2. **SDK (Client Mode)** -> Создает файл `REQ_LASER1_...json` на Samba.

3. **SDK (Master Mode Thread)** -> Видит этот файл через секунду.

4. **Master Logic** -> Проверяет в своей БД, пишет `RES_LASER1_...json`.

5. **SDK (Client Mode)** -> Видит ответ, обновляет `local.db`.

6. **NiceGUI** -> Видит обновление в базе и меняет цвет кнопки.


---

## 5. Почему это круто для FastAPI?

- **Concurrency:** Благодаря `asyncio`, ожидание ответа от Samba не блокирует интерфейс. Рабочий может продолжать листать список, пока "файл летит".

- **Dependency Injection:** Ты можешь использовать `Depends(get_sdk)` в обычных API-эндпоинтах, если планируешь подключать внешние сервисы.

- **Унификация:** У тебя **один и тот же код** на всех 10 лазерах. Весь "умный" выбор происходит динамически в памяти.


### Библиотеки, которые тебе понадобятся:

- **`sqlmodel`**: Для работы с базой.

- **`watchfiles`**: Для эффективного мониторинга появления JSON-файлов в папке Samba.

- **`aiofiles`**: Для асинхронного чтения/записи JSON, чтобы не блокировать Event Loop.

- **`shutil`**: Для атомарных операций (`move`) при управлении чертежами.

Для того чтобы твоя P2P-система работала как единый организм, структура папок на сетевом ресурсе (Samba) должна быть **строго формализована**. Это твой «цифровой полигон», где каждый узел знает свое место.

Вот оптимальная архитектура файловой системы, которая обеспечит работу «Шины», «Склад бэкапов» и «Архив чертежей».

## 1. Топология сетевого диска (Samba Root)

Рекомендую создать одну корневую папку (например, `FACTORY_DATA`), а внутри неё — жесткую структуру:

Plaintext

```
/FACTORY_DATA
├── /BUS                <-- "Шина" (активные сообщения)
│   ├── /INBOX          <-- Сюда узлы кидают REQ_*.json
│   └── /OUTBOX         <-- Сюда Координатор кладет RES_*.json
├── /CLUSTER            <-- "Состояние кластера"
│   ├── .coordinator.lock <-- Файл-замок (Leader Election)
│   ├── /SNAPSHOTS      <-- Сюда Координатор льет JSON-снапшоты (регистр сущностей)
│   └── /HEARTBEATS     <-- Регистрация и статус активных узлов (node_ID.json)
├── /STORAGE            <-- "Склад" (чертежи и файлы)
│   ├── /PENDING        <-- Новые чертежи (из КБ)
│   ├── /ACTIVE         <-- То, что сейчас в работе
│   └── /COMPLETED      <-- Архив выполненных работ
└── /LOGS               <-- Текстовые логи систем для дебага
```

---

## 2. Общение: Механика "Шины" (`/BUS`)

Чтобы папка не превратилась в «свалку», используй разделение на входящие и исходящие:

- **Узел-Клиент:**

    1. Пишет запрос в `/BUS/INBOX/REQ_LASER1_123.json`.

    2. Слушает появление `/BUS/OUTBOX/RES_LASER1_123.json`.

    3. После прочтения ответа — **удаляет оба файла** (или переносит в `/LOGS/HISTORY/YYYY-MM-DD/` для аудита).

- **Узел-Координатор:**

    1. Следит за `/BUS/INBOX/`.

    2. Забирает файл, обрабатывает.

    3. Пишет ответ в `/BUS/OUTBOX/`.


---

## 3. Складирование Снапшотов (`/CLUSTER/SNAPSHOTS`)

Так как любой узел может стать мастером, он должен иметь доступ к самой свежей версии «Правды».

- **Стратегия именования:** `SNAP_{node_id}_{iso_timestamp}.json`.

- **Ротация:** Координатор должен хранить, например, последние 10 снапшотов. Старые — удалять.

- **Механика:** Раз в 5-10 минут (или после серии транзакций) Координатор выгружает регистр domain-сущностей в JSON.

    - Новый Координатор при «захвате власти» ищет в папке файл с самым свежим `timestamp` и делает Merge с локальной базой по правилу LWW (Last-Write-Wins).


---

## 4. Определение "Места жительства" (Конфиг)

В коде твоего SDK это описывается через одну базовую настройку. В FastAPI это лучше всего засунуть в `PydanticSettings`.

Python

```
from pydantic_settings import BaseSettings

class FactoryConfig(BaseSettings):
    # Корневой путь к Samba (монтируется как диск или через UNC путь)
    storage_root: str = "/mnt/factory_data"

    # Вычисляемые пути
    @property
    def bus_inbox(self) -> str:
        return f"{self.storage_root}/BUS/INBOX"

    @property
    def snapshot_dir(self) -> str:
        return f"{self.storage_root}/CLUSTER/SNAPSHOTS"

    node_id: str = "AUTO" # Будет определен при старте
```

## 5. Важный нюанс: Атомарность на Samba

Сетевые папки коварны. Чтобы файлы не читались «наполовину», всегда используй правило:

1. **Запись:** Сначала создай временный файл локально или в той же папке под именем `.tmp_REQ_...`.

2. **Публикация:** Используй `os.rename(tmp_name, final_name)`.

    Это гарантирует, что Координатор не увидит файл `REQ`, пока он не будет полностью записан на диск.

- **Шина:** `/BUS/INBOX` и `/BUS/OUTBOX` (очищаются после транзакции).

- **БД:** `/CLUSTER/SNAPSHOTS` (хранит историю версий мастер-базы).

- **Координация:** Корневой файл `.lock` в `/CLUSTER`.
