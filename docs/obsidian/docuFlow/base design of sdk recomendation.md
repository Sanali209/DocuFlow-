Чтобы правильно смешать **Аллокатор** и **Dependency Injection (DI)** в рамках гексагональной архитектуры, нужно четко распределить роли: **Аллокатор** знает _когда_ создать объект, а **DI** определяет _из чего_ он будет собран.

В Python 3.12+ это превращается в элегантный паттерн, где корень SDK выступает как «Диспетчер ресурсов».

---

### 1. Архитектурная концепция

- **Гексагон (Ядро):** Твои системы (например, `ProductionSystem`), которые принимают зависимости через `__init__` (чистый DI).

- **Порты (Интерфейсы):** Абстракции (через `Protocol`), которые описывают, что система ожидает от внешнего мира.

- **Аллокатор (Инжектор):** Фабрика, которая хранит реестр «реализаций» (адаптеров) и «впрыскивает» их в системы при создании.


---

### 2. Реализация на Python 3.12 (Код-шаблон)

Вот как выглядит этот «коктейль». Мы используем `typing.Protocol` для портов и `Generic` для строгого контроля типов.

``` python
from typing import Protocol, TypeVar, Type, Self, Dict, Any
from sqlmodel import Session

# --- ПОРТЫ (Hexagonal: Interfaces) ---
class ScannerPort(Protocol):
    def scan(self) -> str: ...

class DBPort(Protocol):
    """Интерфейс для работы с данными"""
    def get_session(self) -> Session: ...

# --- ЯДРО (Hexagonal: Domain System с DI) ---
class ProductionSystem:
    def __init__(self, db: Session, scanner: ScannerPort):
        self.db = db
        self.scanner = scanner  # Зависимость впрыснута через конструктор

    def process_part(self, task_id: int):
        code = self.scanner.scan()
        print(f"Обработка детали {task_id} с кодом {code}")

# --- АЛЛОКАТОР + DI ИНЖЕКТОР (The Core) ---
S = TypeVar("S")

class FactorySDK:
    def __init__(self, session: Session, scanner_hardware: ScannerPort):
        self._session = session
        self._scanner = scanner_hardware
        self._instances: Dict[Type[Any], Any] = {}

    def get_system(self, system_class: Type[S]) -> S:
        """
        Аллокатор: управляет жизненным циклом (Singleton).
        Инжектор: подставляет зависимости при создании.
        """
        if system_class not in self._instances:
            # Здесь происходит магия DI:
            # Аллокатор знает, какие адаптеры нужны этой системе.
            if system_class is ProductionSystem:
                instance = ProductionSystem(
                    db=self._session,
                    scanner=self._scanner
                )
            else:
                # Универсальная аллокация для простых систем
                instance = system_class(self._session)

            self._instances[system_class] = instance

        return self._instances[system_class]

# --- АДАПТЕРЫ (Внешний мир) ---
class RealUSBScanner(ScannerPort):
    def scan(self) -> str: return "QR-BUS-123"

class MockScanner(ScannerPort):
    def scan(self) -> str: return "TEST-CODE"
```

---

### 3. Как это работает в жизни (Workflow)

Когда твой FastAPI или мобильное приложение обращается к SDK:

1. **Запрос:** `sdk.get_system(ProductionSystem)`.

2. **Аллокатор** проверяет: «Создавал ли я её раньше в этой сессии?».

3. **Инъекция:** Если нет, он берет «живую» сессию БД и «живой» драйвер сканера (которые были переданы в `FactorySDK` при старте) и передает их в `__init__` системы.

4. **Блокировка:** Внешний код **заблокирован** от прямой работы со сканером или БД. Он видит только методы `ProductionSystem`.


---

### 4. Почему это «правильное» смешивание?

1. **Тестируемость:** Ты можешь создать `FactorySDK` с `MockScanner` и протестировать всю логику производства без реального оборудования.

2. **Гибкость (Hexagonal):** Если ты сменишь сканеры на заводе с USB на сетевые (TCP/IP), ты просто создашь новый адаптер `NetworkScanner` и передашь его в Аллокатор. Код `ProductionSystem` останется **нетронутым**.

3. **Прозрачность (DI):** Глядя на `__init__` любой системы, ты сразу видишь, что ей нужно для работы. Нет «магических» глобальных переменных.


### 5. Рекомендация по именованию

В твоем SDK лучше всего называть это так:

- **`FactorySDK`** — это твой **Аллокатор** (Корень).

- **`ProductionSystem`, `LogisticsSystem`** — это твои **Системы** (Ядро).

- **`Adapters`** — папка с реализациями конкретного железа и БД.


Такая структура позволит твоему проекту автобусного завода расти годами, не превращаясь в запутанный клубок.

## 2. Иерархия компонентов

### **Уровень 1: Аллокатор (Root SDK)**

Это точка входа. Он инициализируется один раз (например, в `lifespan` FastAPI) и хранит реестр адаптеров.

- **Функция:** Выделяет системы и внедряет в них зависимости (сессию БД, драйверы сканеров, API ключи LLM).

- **DI:** Использует область видимости (Scope), чтобы одна сессия БД жила ровно один HTTP-запрос.


### **Уровень 2: Базовая Система (BaseSystem)**

Абстрактный класс, от которого наследуются все бизнес-блоки.

- **Хуки:** `on_before_action`, `on_after_action`.

- **Транзакционность:** Автоматический `commit` при успехе и `rollback` при ошибке.

- **Регистрация:** Каждая система «знает» о корневом Аллокаторе через Generic-типизацию.


### **Уровень 3: Контракты и Адаптеры**

Здесь реализуется «блокатор».

- **Порты (Protocols):** Описывают интерфейсы для LLM, принтеров этикеток и станков.

- **Реестр (Registry):** Позволяет регистрировать разные реализации (например, `GeminiAdapter`, `OpenAIAdapter`) и вызывать их по имени.

## 3. Интеграция с FastAPI (Пример реализации)

Самое удобное — использовать FastAPI `Depends` для внедрения твоего SDK в каждый роут.


``` python
from fastapi import FastAPI, Depends
from sqlmodel import Session
from .sdk import FactorySDK, ProductionSystem

app = FastAPI()

# Функция-провайдер SDK для FastAPI
def get_sdk(session: Session = Depends(get_db_session)):
    # Здесь аллокатор собирает SDK со всеми зависимостями
    sdk = FactorySDK(session=session, llm_provider="gemini")
    return sdk

@app.post("/production/start-task")
async def start_task(task_id: int, sdk: FactorySDK = Depends(get_sdk)):
    # Мы просим аллокатор выдать нужную систему
    production = sdk.get_system(ProductionSystem)

    # Выполняем бизнес-логику. Всё внутри: хуки, логи, транзакции.
    result = production.start_work(task_id=task_id)
    return {"status": "success", "work_id": result.id}
```

## 4. Почему эта концепция «выстрелит»?

1. **Чистота роутов:** В FastAPI-файлах у тебя будет 2-3 строчки кода. Вся сложность завода спрятана в SDK.

2. **Эволюция железа:** Если завтра вы купите новые сканеры или решите перейти с Gemini на локальную модель, ты просто обновишь «Адаптер» в SDK. Веб-сервер и мобильное приложение этого даже не заметят.

3. **Безопасность:** Благодаря «блокатору» (типизации 3.12+), ты не сможешь вызвать метод, который требует сессию БД, не передав её. Ошибки ловятся еще на этапе написания кода.


## 1. Система Конфигурирования (Bootstrapping)

Это «холодная» часть. Она происходит **один раз** при старте приложения (например, в `lifespan` FastAPI).

- **Где хранится:** Переменные окружения (`.env`), файлы `yaml/toml` или секреты (HashiCorp Vault).

- **Что внутри:**

    - Строка подключения к БД (DB_URL).

    - API-ключи для LLM (Gemini/OpenAI).

    - Уровень логирования (DEBUG/INFO).

    - Порты и хосты.

- **Роль в Аллокаторе:** Конфигурация диктует Аллокатору, какие **Адаптеры** загружать. Если в `.env` написано `SCANNER_TYPE=usb`, Аллокатор подгрузит плагин для USB-сканера.


---

## 2. Система Настроек (Runtime Settings)

Это «горячая» или **реактивная** часть. Она живет внутри твоего SDK как отдельная `SettingsSystem`.

- **Где хранится:** В БД через **SQLModel** (таблица `system_settings`).

- **Что внутри:**

    - Бизнес-правила: `max_weight_per_bucket`, `require_otk_approval`.

    - Флаги режимов: `maintenance_mode: true`.

    - Промпты для LLM: `current_extraction_prompt`.

- **Реактивность:** Когда админ меняет значение в БД через UI, SDK должен мгновенно (или с коротким кешем) начать использовать новое значение без перезагрузки сервера.


---

## 3. Как это выглядит в архитектуре SDK

### Реализация `SettingsSystem` (Реактивная часть)

``` python
from typing import Any, Optional
from sqlmodel import select, Session

class SettingsSystem(BaseSystem):
    """Система для работы с динамическими настройками из БД"""

    def get(self, key: str, default: Any = None) -> Any:
        # 1. Пробуем взять из локального кеша сессии (чтобы не спамить в БД)
        # 2. Если нет — запрашиваем через SQLModel
        statement = select(SystemSetting).where(SystemSetting.key == key)
        setting = self.session.exec(statement).first()

        if not setting:
            return default

        return setting.value # Здесь можно добавить десериализацию из JSON

    def set(self, key: str, value: Any):
        # Обновляем в БД и инвалидируем кеш
        setting = self.session.get(SystemSetting, key) or SystemSetting(key=key)
        setting.value = value
        self.session.add(setting)
        self.session.commit()
```

## 4. Интеграция в жизненный цикл (Хуки)

Самая мощь проявляется, когда ты используешь **Настройки** внутри хуков `BaseSystem`.


``` python
class ProductionSystem(BaseSystem):
    def on_before_action(self, action_name: str, **kwargs):
        # РЕАКТИВНОСТЬ: проверяем настройку прямо перед выполнением
        is_blocked = self.sdk.settings.get("block_production", default=False)
        if is_blocked and action_name == "start_task":
            raise PermissionError("Производство временно остановлено через настройки.")
```

## 5. Итоговая схема взаимодействия

1. **Запуск (Config):** FastAPI читает `.env` -> Создает `Engine` для БД -> Инициализирует `FactorySDK`.

2. **Работа (Settings):** * Рабочий сканирует деталь.

    - `ProductionSystem` спрашивает у `SettingsSystem`: «А нужно ли сейчас делать фото фиксацию?».

    - `SettingsSystem` лезет в БД, видит `need_photo: True`.

    - SDK требует фото.

3. **Изменение:** Админ в приложении выключает `need_photo`. Настройка в БД меняется, и следующий рабочий уже не обязан делать фото. **Сервер не перезагружался.**


### Подходящие библиотеки для этого:

- **Pydantic-Settings:** Идеально для первого этапа (Конфигурирование из `.env`).

- **SQLModel:** Для второго этапа (Настройки в БД).
