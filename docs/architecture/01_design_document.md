> **Статус:** Living document — обновляется с каждой итерацией плана
> **Приоритет источников:** Текущий код > этот документ > Obsidian канвас

## 1. Назначение системы

DocuFlow — это распределённая производственная информационная система для цеха металлообработки. Она заменяет ручной бумажный учёт работ, устраняя проблемы:

| Проблема (сейчас) | Решение (DocuFlow) |
|---|---|
| Никто не знает, где лежат готовые детали | ProductionUnit + StorageLocation + поиск |
| GNC файлы изменились, оператор режет старую версию | NSMirrorService + хэш-мониторинг |
| Бригадир ведёт учёт на бумаге / голове | WorkItem + TaskItem + WorkerBucket |
| Нет синхронизации между лазерами | P2P FileBus + snapshot/sync |
| Расходники кончаются внезапно | Consumable + min_quantity алерт |
| Не фиксируются инциденты и простои | IncidentLog + WorkLog |
| Нет истории: кто, когда, что сделал | WorkLog (полный аудит) |
| Папка пришла, нестов нет — узнают позже | PENDING_CUTS статус + чат-алерт |

---

## 2. Контекст цеха

- **Производство:** Детали из листового металла для автобусов (Apollo и др.)
- **Оборудование:** Лазеры для резки металла. Каждый лазер = `Workplace` (узел системы)
- **Смены:** 2 смены
- **Роли:** Оператор (режет), Бригадир (планирует), Начальник (контролирует), Кладовщик (склад), Админ (IT)
- **Совмещение ролей:** Оператор + Бригадир может быть один человек
- **Среда:** Windows на всех машинах
- **Сеть:** Samba / CIFS сетевой диск (буква диска разная на каждом ПК)
- **Ограничение:** Нет прямого TCP между узлами — вся связь через файловую шину на сетевом диске

## 3. Источники данных

### 3.1 GNC файлы (основной источник)

Файлы программ резки для лазерного станка. Содержат:

```
(*SHEET 3250.0 1250.0 3.0 7 1 0.0 0.0)
  → sheet_x=3250, sheet_y=1250, thickness=3.0, sheet_qty=7
(Material:AA 5052-H32)
  → MaterialType.code
(PART NAME:3433-11-004-G-1)
  → SKU = "3433-11-004-G", version = "1" (отбрасывается)
(==== CONTOUR 1 ====)
  → G-код контуров → bbox_x/y через SVGGenerator
```

**Правило:** `_AUT.TXT` и `.Dsp` файлы игнорируются как ненадёжные.

### 3.2 Имена папок

```
SIDRA-353203-SHLAV-2-07.07.2025
  → sidra_number="353203", sidra_step="SHLAV-2", doc_date=2025-07-07
```

Если не парсится → fallback: `work_item_type=MIHTAV`, `project="Default"`.

### 3.3 Физические документы (бумажные наряды)

Регистрируются вручную бригадиром. Не сканируются, не парсятся. Только факт получения (`doc_received_at`).

## 4. Операционный цикл (8 этапов)

```
1. ПОЛУЧЕНИЕ РАБОТЫ
   Сканер → обнаруживает папку:
     С GNC:  WorkItem(NEW)         → чат-уведомление
     Без GNC: WorkItem(PENDING_CUTS) → алерт "нет нестов, сходить в раскрой"
   Бригадир → регистрирует бумажный документ → WorkItem(REGISTERED)

2. ПОДГОТОВКА К РАБОТЕ
   Бригадир → проверка материалов → Reservation (soft)
   Если нет → дозаказ → ChatMessage(type=ORDER)
   BatchEngine → автогруппировка TaskItem по MAT+THK+SIZE
   Бригадир → редактирует батчи → комментирует → приоритеты
   Проверка запаса → STOCK_ALERT если деталь уже есть

3. ПРИЁМ В РАБОТУ
   Оператор → видит батчи → резервирует → WorkerBucket
   FileBus REQ: lock_batch → Мастер подтверждает
   NSMirrorService → копирует GNC в локальную NS папку

4. ВЫПОЛНЕНИЕ
   Оператор → меняет статус (planned → in_progress → on_hold → done)
   Трекинг листов: sheets_done++
   Оценка: estimated_minutes vs actual_minutes → drift%
   Инциденты → IncidentLog + ChatMessage(type=INCIDENT)

5. ЗАВЕРШЕНИЕ
   TaskItem(DONE) → диалог "куда кладём?"
     Новая паллета: ProductionUnit(label_id="25-07-А-042")
     К существующей: live search по части label_id
   MaterialAudit(write_off) → факт списания листов

6. СКЛАДИРОВАНИЕ
   ProductionUnit → StorageLocation
   Поиск: по label_id / SKU / work_item / материалу
   Обратный поиск: деталь → паллета → стеллаж
   Split/merge паллет, частичный перевод в запас

7. РЕТРОСПЕКТИВНЫЙ ПОИСК
   PartLibrary: по SKU / bbox±допуск / кол-во отверстий / текст
   "В каких нарядах эта деталь?" "Где она сейчас?"

8. УПРАВЛЕНИЕ СКЛАДОМ
   MaterialStock: приход / списание / инвентаризация
   Consumable: сопла, линзы, лента + критический остаток
   MaterialAudit: полный аудит всех движений
   Передача смены: WorkerBucket handover + аннотации
```

## 6. Ключевые технические решения

| Вопрос | Решение | Обоснование |
|---|---|---|
| Кто сканирует | Только мастер-узел | Один источник правды |
| Триггер сканирования | Periodic polling (async) | Samba не поддерживает inotify надёжно |
| Хранение путей | Только относительные | Буква диска разная на каждом ПК |
| Изменение файлов | MD5 hash + WorkLog | Детекция без перемещения |
| Исходные файлы | Не трогаем | Сеть = read-only источник |
| Синхронизация узлов | FileBus + Snapshot | Нет TCP соединений |
| GNC → локальный диск | NSMirrorService | Автоматика читает из локальной NS папки |
| ID паллеты | "25-07-А-042" (human-readable) | Нет QR-сканера, нужен ввод вручную |
| Конфигурация путей | LOCAL .env | Глобальная синхронизация недопустима |
| Bbox детали | SVGGenerator.calculate_bounds() | PART SIZE = bbox неста, не детали |

## 7. Границы системы (in/out of scope)

### В рамках системы
- Автоматическое обнаружение нарядов по сетевой папке
- Управление производственными задачами (batch/task/status)
- Учёт материалов, расходников, готовой продукции
- Оперативная коммуникация (чат с типами сообщений)
- Ретроспективный поиск деталей и нарядов
- Отчёты по шаблонам (HTML → PDF)
- NS-зеркало GNC файлов для операторов

### Вне рамок системы
- Интеграция с ERP завода (не планируется в v1)
- Автоматическое создание нарядов из внешних систем
- Управление станком (только мониторинг)
- Мобильное приложение (только Windows desktop NiceGUI)
- Резка труб и прутков (backlog, не MVP)
